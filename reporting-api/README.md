# Cash Runway Reporting API

Text-only feedback intake for Cash Runway.

The iOS app posts bug/improvement reports to `POST /api/reports`. The API validates and sanitizes the report, then creates a GitHub issue server-side through a GitHub App installation token.

## Payload

```json
{
  "category": "bug",
  "idempotencyKey": "a4c0af2f-73cb-4d35-a47e-7ef273fd82d1",
  "title": "CSV import crashes",
  "description": "The app crashes after selecting a CSV file.",
  "screen": "CSVImportView",
  "screenshots": [
    { "data": "base64...", "mimeType": "image/jpeg", "filename": "screenshot-1.jpg" }
  ],
  "appVersion": "1.0.0",
  "buildNumber": "42",
  "iosVersion": "18.7",
  "deviceModel": "iPhone15,4",
  "locale": "uk-UA",
  "timezone": "Europe/Uzhgorod",
  "installHash": "sha256..."
}
```

## Safety

Users can voluntarily attach up to 3 screenshots to a report. Screenshots are compressed on the device, validated as JPEG/PNG by magic bytes, and uploaded to the configured GitHub repository so they render inline in the created issue. Logs, CSV files, database files, balances, transactions, and Monobank tokens are never accepted.

The API enforces `application/json`, a 4 MB request body limit (base64-encoded screenshots), duplicate suppression for 24 hours, and Redis-backed limits:

- 3 reports/hour per `installHash`
- 10 reports/day per `installHash`
- 10 reports/hour per IP when `installHash` is missing

Server logs must not include report title or description. Only safe metadata is logged: report id, category, screen, app version, status, issue number, and duration.

## Setup

Copy `.env.example` into Vercel environment variables after creating and installing the GitHub App. The app needs **Issues: write** and **Contents: write** permissions on `romanr111/cash-runway`.

Required enabled configuration:

- `REPORTING_ENABLED=true`
- `CASH_RUNWAY_REPORT_SECRET`
- `GITHUB_APP_ID`
- `GITHUB_APP_INSTALLATION_ID`
- `GITHUB_APP_PRIVATE_KEY`
- `GITHUB_REPO_OWNER`
- `GITHUB_REPO_NAME`
- `KV_REST_API_URL`
- `KV_REST_API_TOKEN`

Set `REPORTING_ENABLED=false` to fail closed with HTTP 503 without creating issues.

Use separate Vercel projects or environment variable sets for staging and production. Point debug iOS builds at local/staging endpoints; release builds should only receive the production endpoint and shared client secret through build configuration.

### iOS client secret

The iOS app's shared client secret is **not stored in `Info.plist`**. It is obfuscated at build time in `Sources/CashRunwayCore/ReportingSecrets.generated.swift`, generated by `Scripts/generate-reporting-secrets.swift` from `AppHost/ReportingConfig.local.xcconfig` (git-ignored). On first launch the deobfuscated secret is moved to the Keychain and read from there thereafter.

After editing `AppHost/ReportingConfig.local.xcconfig`, regenerate the secret file:

```bash
Scripts/generate-reporting-secrets.swift
```

The Xcode build target also runs this script automatically. **Do not commit `ReportingSecrets.generated.swift` if it was regenerated with a real secret.** The committed placeholder version uses `isPlaceholder = true` so reporting is treated as not configured.

## Staging E2E Readiness

1. Create a GitHub App with **Issues: write** and **Contents: write**.
2. Install it on `romanr111/cash-runway`.
3. Create an Upstash Redis database and copy the REST URL/token into Vercel.
4. Create a Vercel staging project with the enabled environment variables above.
5. Configure a debug build with the staging endpoint and client secret.
6. Submit one report with a screenshot from Simulator/device and confirm the GitHub issue renders the image inline.
7. Re-submit the same report and confirm the API returns a duplicate/rate-limit error instead of creating another issue.

```bash
npm install
npm test
npm run typecheck
```
